# The Hiring Gate: Whether an Applicant Tracking System Commits the Screen or Stores It for a Manager to Decide

A candidate applies, an applicant tracking system (ATS) screens the application, and a hiring manager rules on who advances. This is a stand-alone qualitative study, pre-registered here as a scaffold: it reads the ATS hiring gate against the strict-bottleneck prior and asks whether the system commits a determination the manager must heed or stores and surfaces data the manager rules on alone, and where the candidate, the system, and the manager each locate the decision. No fieldwork has been done and no findings are claimed; the interview guide, bit calibration, and falsification conditions are committed in `coding_scheme.md` before any data, so the git history shows the questions were fixed before the answers.

## Fit

Whether a screening system commits a determination or merely stores data for a human is a question about practice, not topology: the same arrangement can do either, and which it does is visible only in how the parties actually run a screen — whether a manager can reach past the system's cut, and whether anyone ever sees the applications the system removed. Qualitative inquiry — rule-elicitation interviews, document and log analysis, and worker folk-theory elicitation — is built to recover the rule each party acts on and the rule the system applies that the parties theorize from the outside.

## The prior

The nearest prior is the strict bottleneck (`ats_strict_bottleneck` in [`../corpus/forms_library.py`](../corpus/forms_library.py)) read against its factoring twin (`ats_feedback_factors`): the same topology can commit a screen the manager must heed, or merely store and surface data the manager rules on alone. The prior sets the commit-versus-convey line as the thing the field decides. It is held open: the setting departs from the bottleneck toward factoring if managers routinely and successfully reach past the system's cut, and the candidate departs from object toward party if gaming the filter co-determines which applications advance. The departure is where the contribution would be built. (This study is a pre-registration scaffold; the departures are named in `coding_scheme.md` as falsification conditions, not reported as found.)

## Setting and boundary

The recurring act is the screening of one application: a candidate submits, the ATS applies a knockout or ranking rule, and a hiring manager rules on the surfaced shortlist. The boundary holds three parties — candidate, ATS, hiring manager — and excludes the wider hiring committee except where it bears on whether the manager can reach past the system's cut. What repeats is the per-application screen.

## Parties

- **Candidate (C)** — holds the application and updates it to clear the filter. Candidate for *substitution* (one of many interchangeable applicants) and a candidate for *object* rather than party, if the screen happens to it without its co-determining the outcome.
- **ATS (S)** — applies the screening rule. Candidate for *third party that commits* if its cut is final, or for *store-and-surface medium* if the manager rules past it.
- **Hiring manager (M)** — rules on the shortlist. Candidate for the party that holds the decision, if the system only surfaces.

## Contribution

The study aims to refine the strict-bottleneck prior by specifying the conditions under which an ATS commits the screen in practice versus stores it for a manager, and the lived shape of candidate substitutability and filter-gaming. Stated here as the intended contribution so a later study, with data, can deliver it.

## Limits and what would falsify this

The falsification conditions are committed in advance in [`coding_scheme.md`](coding_scheme.md): the prior departs toward factoring if managers reach past the cut; the candidate is a party if gaming co-determines the screen; the system's rule is unrecoverable if no party or document discloses it.
